1 Introducción

1.1 Propósito
Este documento explica qué hace BORROWAPP y cómo lo hace. BORROWAPP es una aplicación móvil
donde las personas de una comunidad cerrada (una universidad, una empresa o un conjunto residencial)
piden objetos prestados o alquilados a sus propios compañeros o vecinos.

El documento define los requisitos funcionales y no funcionales del sistema. Sirve de base para diseñar,
programar y probar la aplicación, y está escrito para el equipo de desarrollo y para el docente que
evalúa el curso. La idea es que cualquier persona que lo lea entienda el comportamiento completo de la
app sin tener que preguntarle nada al equipo.


1.2 Alcance del Producto
La aplicación cubre el recorrido completo de un préstamo: alguien publica lo que necesita, otro
miembro ofrece el objeto, el solicitante acepta, se hace la entrega, se usa el objeto, se devuelve y todo
queda guardado en el historial.

Un ejemplo corto: Camilo necesita un taladro por tres días. Lo publica en la app. Jesús, que tiene uno,
responde con sus condiciones: lo alquila a $10.000 por día. Camilo acepta, se encuentran en la
Biblioteca Central, los dos confirman la entrega en la app, y tres días después hacen lo mismo con la
devolución. Camilo le paga a Jesús en persona.

Lo que la app no hace: no mueve dinero y no entrega objetos. Solo organiza y registra el proceso. La
entrega, la devolución y el pago pasan en persona, en el punto central que define cada organización.
Esta versión no incluye:
   • Pagos, tarjetas o billeteras digitales dentro de la aplicación.
   • Chat interno, videollamadas ni mensajería.
   • Mapas, GPS ni seguimiento en tiempo real. El punto central se muestra solo como texto.
   • Códigos QR.
   • Domicilios ni repartidores.
   • Recomendaciones ni clasificación automática con inteligencia artificial.
   • Verificación de identidad con documentos oficiales.
   • Fotos de los objetos. Cada objeto se representa con un ícono de categoría.
   • Calificaciones con estrellas, sistema de reputación, multas automáticas o depósitos de garantía.

2 Descripción General

2.1 Perspectiva del Producto
BORROWAPP es un producto nuevo; no reemplaza ningún sistema existente. Es una aplicación móvil
construida en Flutter que se comunica mediante una API REST propia con una base de datos PostgreSQL.
No se integra con los sistemas internos de cada organización (por ejemplo, no valida contra el sistema
académico de una universidad ni contra el sistema de nómina de una empresa): el vínculo de un usuario
con su organización se resuelve por completo dentro de la propia app, mediante el código de acceso de
5 caracteres que el sistema genera al crear cada organización.

Quien crea una organización construye, en la práctica, una red cerrada de préstamo entre las personas
de su comunidad: queda automáticamente como su administrador y recibe el código que debe
compartir con los demás para que se unan.

2.2 Modelo de Organizaciones y Pertenencia Múltiple
Este es el punto que más se amplía respecto a la versión 1.0, porque de él depende buena parte de los
demás requisitos. Un usuario de BORROWAPP no pertenece a una sola comunidad: puede unirse a
tantas organizaciones como quiera (por ejemplo, su universidad y el conjunto residencial donde vive), y
dentro de cada una tiene una condición propia e independiente de las demás.

Las reglas exactas son:
   • La relación entre un usuario y una organización se llama Membresía. Un usuario tiene
     exactamente una membresía por organización a la que pertenece, y puede tener varias
     membresías simultáneas (una por organización).
   • Cada membresía guarda su propio rol (Administrador o Miembro), su propio estado (Activo,
     Advertido, Suspendido o Baneado) y su propio identificador interno (código estudiantil, código de
     empleado o número de apartamento, según el tipo de organización). Ninguno de estos tres datos
     se comparte entre organizaciones.
   • El rol de Administrador lo tiene únicamente quien creó la organización, y solo dentro de ella. En
     cualquier otra organización a la que ese mismo usuario se una después, su rol es Miembro. Este
     MVP no contempla transferir la administración ni nombrar administradores adicionales.
   • La "organización activa" es el filtro que decide qué ve el usuario en pantalla en cada momento
     (necesidades, ofertas, préstamos e historial). Es un dato de la sesión del usuario, no de su cuenta:
     cambiarla no modifica ninguna membresía.
   • Una sanción o una suspensión aplicada en una organización nunca afecta las membresías del
     usuario en las demás.

2.3 Funciones Principales del Producto
   • Registro e inicio de sesión de usuarios.
   • Creación de una organización (con generación automática de su código de acceso de 5 caracteres)
     y unión a una organización existente mediante ese código.
   • Cambio de la organización activa, para usuarios con más de una membresía.
   • Publicación y consulta de necesidades de objetos dentro de la organización activa.
   • Creación de ofertas de préstamo gratuito o alquiler en respuesta a una necesidad, y aceptación o
     rechazo de esas ofertas por parte de quien la publicó.
   • Gestión del préstamo resultante: confirmación cruzada de entrega y de devolución, hasta su
     finalización.
   • Historial y estadísticas básicas de la actividad del usuario, diferenciando su papel como solicitante
     o como prestador.
   • Reporte de problemas sobre un préstamo y, para el administrador de la organización
     correspondiente, un panel para atenderlos y aplicar sanciones.

2.5 Restricciones
   • La aplicación móvil se desarrollará en Flutter y Dart.
   • El backend se construirá como una API REST propia.
   • La base de datos será PostgreSQL.
   • El código de acceso de una organización tiene exactamente 5 caracteres alfanuméricos en
     mayúsculas, se genera automáticamente y debe ser único en todo el sistema.
   • El proyecto debe completarse aproximadamente en 14 semanas.
   • No se incluirá pasarela de pagos ni manejo de dinero dentro de la aplicación.
   • No se utilizarán mapas, GPS ni códigos QR en esta versión.
   • El presupuesto de hosting está limitado a servicios gratuitos o de bajo costo (Railway, Render,
     Vercel).

2.6 Suposiciones y Dependencias
   • Se asume que los usuarios cuentan con un smartphone y acceso a Internet.
   • Se asume que cada organización define y mantiene actualizado su punto central de entrega y
     devolución.
   • Se asume que los usuarios cumplen entre ellos los acuerdos de entrega, devolución y pago, sin
     intervención de la aplicación.
   • El sistema depende de que el administrador de cada organización comunique correctamente el
     código de acceso a sus miembros.
   • Se asume que los objetos se prestan y se reciben en buenas condiciones.
   • Se asume que no hay organizaciones o comunidades duplicadas.
   • Se asume que cada organización tiene un único administrador, que es quien la creó; este MVP no
     contempla transferir ni compartir ese rol.
   • Se asume que un usuario puede pertenecer a cualquier número de organizaciones, sin un límite
     definido en este MVP.
   • Se asume que el identificador interno (código estudiantil, de empleado o de apartamento) es un
     campo de texto libre: la aplicación no lo valida contra un sistema externo de la organización.

Lectura del flujo, paso a paso:
   • Un usuario publica una necesidad indicando el objeto, una descripción y las fechas en que lo
     requiere (RF-006). Queda visible solo para los miembros de su organización activa (RF-007), con
     estado Buscando prestador.

   • Cualquier otro miembro de esa misma organización que tenga el objeto puede responder tocando
     "Tengo este objeto". Es en ese momento, y no antes, cuando se definen las condiciones del
     préstamo: si es gratis o de alquiler, y si es alquiler, el precio, la unidad de cobro (hora o día) y la
     fecha y hora en que puede entregarlo (RF-008). Esto crea una oferta en estado Pendiente.
   • Pueden existir varias ofertas pendientes para la misma necesidad, una por cada miembro que
     respondió. El solicitante las revisa y decide, oferta por oferta, aceptar o rechazar (RF-010).
     Rechazar una oferta no cierra la necesidad: las demás siguen abiertas y cualquier otro miembro
     puede seguir ofreciendo mientras la necesidad esté en Buscando prestador.
   • Al aceptar una oferta, el sistema cierra automáticamente todas las demás ofertas pendientes de
     esa necesidad (RF-010) y crea el préstamo correspondiente, en estado Confirmado, con el objeto,
     las dos partes, las fechas, el precio total y el punto central de la organización (RF-011). La
     necesidad pasa a Con préstamo confirmado.
   • La entrega ocurre en persona, en el punto central. El préstamo solo avanza a Activo cuando las dos
     partes la confirmaron desde la aplicación: primero el prestador marca "Entregado", y luego el
     solicitante confirma "Recibido" (RF-012). En cuanto el prestador marca Entregado, el préstamo se
     muestra en Entrega pendiente hasta que el solicitante confirme.
   • La devolución sigue la misma lógica en sentido inverso: el solicitante marca "Devuelto" y el
     prestador confirma la recepción. Solo con ambas confirmaciones el préstamo pasa a Finalizado
     (RF-013), y la necesidad se cierra.
   • Si en cualquier punto entre Confirmado y Devolución pendiente una de las partes reporta un
     problema (objeto no devuelto, objeto dañado o inasistencia de la otra parte), el préstamo se
     marca En conflicto mientras el administrador de la organización lo revisa (RF-014). Esta marca no
     borra el progreso del préstamo: por debajo, el préstamo conserva su estado real y, una vez
     resuelto el reporte, continúa su flujo normal hasta Finalizado (RF-018). La sección 3.3 detalla esta
     máquina de estados.
   • Toda la operación —necesidad, oferta y préstamo— queda disponible después en el historial de
     ambos usuarios, marcando el papel de cada uno como solicitante o como prestador (RF-015).

3.4 Reglas de Negocio Explícitas
Esta lista reúne, en un solo lugar y sin tecnicismos, las reglas que gobiernan el comportamiento del
sistema y que están repartidas en los requisitos anteriores. Su propósito es que una persona que lea
solo esta sección entienda el comportamiento completo de la aplicación sin ambigüedad.

   • Un usuario puede tener varias membresías, una por organización; su rol, su estado y su
     identificador interno son independientes en cada una.
   • El código de una organización tiene siempre 5 caracteres alfanuméricos en mayúsculas y es único
     en todo el sistema.



BORROWAPP · Especificación de Requisitos de Software · Versión 2.0                                  Página 16 de 33
   • Solo el creador de una organización es su administrador; no existe transferencia ni asignación de
     administradores adicionales en este MVP.
   • Cualquier miembro activo puede publicar necesidades y también responder a las de otros: ser
     solicitante o ser prestador son papeles de cada operación, no roles fijos de la cuenta.
   • Es el prestador —nunca el solicitante— quien define las condiciones de una oferta: modalidad,
     precio, unidad de cobro y fecha de entrega.
   • Al aceptar una oferta, todas las demás ofertas pendientes de esa misma necesidad pasan a
     Cerrada automáticamente; no es necesario rechazarlas una por una.
   • Un préstamo nunca avanza de estado sin las dos confirmaciones correspondientes: en la entrega,
     la del prestador y la del solicitante; en la devolución, la del solicitante y la del prestador.
   • "En conflicto" es una marca visual superpuesta mientras un reporte está Pendiente; no sustituye
     ni borra el estado real del préstamo, que se retoma tal como estaba al resolver el reporte.
   • Las sanciones (Advertido, Suspendido, Baneado), igual que el rol, son por organización: afectan
     solo la membresía donde ocurrió el reporte que las originó.
   • Un usuario Suspendido o Baneado en una organización puede seguir usando con total normalidad
     cualquier otra organización a la que pertenezca.
   • Los préstamos activos de un usuario sancionado no se cancelan ni se alteran de forma retroactiva
     por la sanción.
   • Una suspensión temporal termina automáticamente al llegar su fecha de fin, sin que el
     administrador tenga que intervenir.
   • La aplicación nunca mueve dinero: cualquier pago acordado ocurre en persona, directamente
     entre las dos partes, en el punto central.

3.5 Requisitos de Interfaces Externas
Interfaz de usuario: interfaz móvil desarrollada en Flutter, con una barra de navegación inferior fija
entre Inicio, Necesidades, Mis préstamos, Historial y Perfil. En la parte superior de estas pantallas
principales se muestra siempre una píldora con la organización activa, que permite cambiarla. Prioriza
formularios simples y estados visuales claros del préstamo (confirmado, entrega pendiente, activo,
devolución pendiente, finalizado, en conflicto). Para los administradores, la interfaz se extiende con un
panel de administración accesible solo dentro de la organización que administran.

Interfaces de software: API REST propia entre la aplicación Flutter y el backend, con comunicación
mediante HTTP y JSON. El backend se conecta a una base de datos PostgreSQL para el almacenamiento
de usuarios, organizaciones, membresías, necesidades, ofertas, préstamos y reportes.

Interfaces de hardware: no se requiere hardware específico. El sistema funciona en cualquier
smartphone con Android o iOS capaz de ejecutar una aplicación Flutter.

4.3 Reglas de integridad
Estas reglas las debe hacer cumplir la base de datos o el backend, no solo la pantalla:
      • El correo de un usuario y el código de una organización son únicos en todo el sistema.
      • Un usuario no puede tener dos membresías en la misma organización.


BORROWAPP · Especificación de Requisitos de Software · Versión 2.0                                            Página 22 de 33
   • Una necesidad, una oferta o un préstamo solo se pueden consultar o modificar por usuarios con
     membresía en la organización a la que pertenecen.
   • Una necesidad nunca tiene dos ofertas en estado ACEPTADA.
   • Un préstamo no cambia a ACTIVO sin las dos confirmaciones de entrega, ni a FINALIZADO sin las
     dos de devolución.
   • El prestador de una oferta no puede ser el solicitante de la necesidad.
   • Un reporte RESUELTO siempre tiene sanción, administrador, fecha y nota de resolución.
   • Al aceptar una oferta, el cambio de estado de la oferta, el cierre de las demás y la creación del
     préstamo se guardan juntos: o pasa todo o no pasa nada (ver RNF-007).
